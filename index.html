Why sensitive data?

- Research uses data - Research can produce results that benefit society - Some data useful for research is sensitive including - Medical data - Administrative data - Financial data - If we don't use it, we loose the benefits - **LINK:** But using sensitive data can be difficult

Why TREs?

- Justified privacy and security concerns - TREs are a solution to that conflict - Make more sensitive data available for research - Compared to sending data to researchers - Prevents unauthorised disclosure - Trust is more distributed (enables 5 safes) - **LINK: ****However**, should provide tools to help researchers work effectively - What does that look like? - Sometimes TREs focus on security at the expense of - Productivity - Reproducibility - Effectiveness

Security maximalism

- We need to handle sensitive data with care and respect - It is therefore tempting to do everything you can do increase security - This is the security maximalist approach - However, - Not all changes are significant (security theatre) - _e.g._ periodic password reset - Some may hamper research - Some may even cause more harm than good - Extra maintenance burden - Extra admin burden - Loss of productivity

In reality

- **You cannot eliminate risk** - Every piece of work starts with a negotiation about what _acceptable_ risk is - You need to balance the value of the outputs with the risk of disclosure

One size does not fit all

No single security configuration for all work

One configuration = the most strict

In DSH

Set of security tiers with technical and policy controls

- There is no single set of security rules suitable for all work - If you only have one, it will be for the most sensitive data you handle - Everyone else will suffer from unnecessary restrictions - In DSH: - We have created a set of tiers which apply to workpackages of different sensitivities - These tiers work for us, but others will likely want to establish a different set - Tiers correspond to sets of security controls

Vulnerability is not the same in a TRE

Even malicious code may not be a significant risk

Should be robust to privilege escalation and bad actors

In DSH

Data flow is restricted at the infrastructure level

Allow packages from CRAN and PyPI

- Donald Scobbie's (EPCC) way of thinking - Existing ways of assessing threat like CVE don't apply well to TREs - For example, network exploits are likely of no concern as there will be no way to use them - Bringing in malicious code isn't much of a concern if the worst you can do is trash your workspace - A TRE should be robust to privilege escalation and bad actors - In DSH: - We take the approach that the environments should be secure to attack from inside - We allow researchers to install packages from CRAN/PyPI themselves - Network is restricted at an infrastructure level - Even privilege escalation does not allow data egress - Lesson: - There doesn't have to be a trade off between usability and security here

Egress is more dangerous than ingress

New data can elevate risk

Top priority: prevent unapproved data egress

In DSH

Moving towards easier data ingress routes

- Introducing data (particularly code) can benefit research - Avoids duplication - Encourages reproducibility - But, Bringing data in could elevate risk/sensitivity - _e.g._ example a key to reidentify individuals in a psuedonymised data set - If your environment is secure, the disclosure is extremely limited (to only people with access) - Fundamentally, you want to prevent unapproved data disclosure - Data ingress doesn't have to make that more likely - In DSH: - We have been moving to better support ingress of data researchers need, particularly code.

Plan ahead

Outputs must be checked

No outputs means wasted time/money

In DSH

Work package classification

- Because outputs might disclose sensitive data, they must be checked - This is particularly difficult in AI/ML. - How can we ensure a model doesn't disclose sensitive data? - If you reach the end of a piece of work but can't release the outputs, it was a waste of time and money. - In DSH: - We define (holistic) work packages, which are not just input data but _all_ input data and the intended outputs - Assess risk in advance to avoid surprises (maybe this is a different lesson, plan ahead?)

Certifications are not security

Certifications don't make a system a TRE

May distract from what is important

In DSH

SATRE

Data Security and Protection Toolkit (NHS)

- Data owners may ask for specific certifications - These are often a good sign of following best practice - However - they do not guarantee security - they do not ensure the kinds of processes/controls necessary for a safe TRE - Focusing your requirements for a TRE on a certification is unhelpful, and possibly dangerous - It may distract from the actual essential qualities of a TRE - In DSH: - SATRE - We collaborated on creating the first "specification" for a TRE - Identifying what the essential qualities of a TRE are - DSPT which is necessary for handling NHS data - Investigating ISO27001

Technical controls are not sufficient

Technical solutions for a people problem

There is no technology to prevent disclosure

In DSH

Technical controls in combination with policy

User training

- There is a tendency for people to ask/imagine/wish for a technical solution to a people problem - Ultimately, we cannot prevent disclosure with technology - _e.g._ - Egress is trivial - camera - pen and paper - screenshots (automated) - Ingress is trivial - keyboard macros/rubber ducky - Demonstration using Keybow2040 - typing out documents - Use non-technical controls when - There is no technical solution - **and** when a technical solution is impractical/expensive - Think back to the five safes, safe people, safe policies - In DSH: - We use both policy and technical controls - User training - Users understand their responsibilities and the potential harms - Openly published documentation for production processes - We are happy for others to use, modify, contribute to these

Communication solves problems

Data owners can have a skewed impression of risk

If you run a TRE, you are an expert

In DSH

Explain the trade off between security and productivity

Aim to find a good balance

- Data owners can have a skewed impression of risk - May ask for specific, overbearing restrictions/requirements - Often request higher security than is necessary (maximalist) - They are strongly incentivised to minimise the likelihood of disclosure - If you operate a TRE, *you* are an expert - Trust your experience - You shouldn't always do what you are asked - In DSH: - We have collaborators who greatly overestimated the security needed - Explain how restrictions hinder work - Arrive at a more reasonable set of controls and make work more productive

Develop outside, run inside

- Encourage users to develop their tools, analysis outside the TRE - Bring into the TRE to run against the sensitive data - Why? - Enables researchers to use their preferred tools - Better enables best practice (open source, version control, CI) - Prevents code outputs of research being lost or stuck inside TREs

Develop outside, run inside

- Implementation - Gitea instance - Function apps to interact with Gitea API - Potential for management system for requests (researchers, admins) - And - As always, this is in the open - Tracked in our milestones and project roadmap - Policies/processes are shared
